Guía de usuario y referencia técnica

Documentación de AOVGuard

AOVGuard valida archivos OpenEXR y secuencias de render. Detecta errores de lectura, NaN, infinitos, AOVs vacíos, canales desconocidos, cambios temporales y problemas de continuidad sin ocultar datos no reconocidos.

Candidata 1.4.0rc1: incorpora controles de memoria, ejecución aislada, rangos técnicos opcionales, reportes protegidos y verificación reproducible con renders existentes. La suite desde código extraído en Windows/Python 3.12.12 supera 1041 pruebas, con 3 omitidas y 96,34 % de cobertura combinada. Es una versión previa a 1.4.0 estable; los paquetes 1.3.0 se conservan separados.

Instalación

Se recomienda Windows o Linux, Python 3.12 y uv. El proyecto admite Python 3.11 y 3.12 y requiere OpenEXR 3.3 o posterior.

cd "C:\ruta\AOVGuard"
python -m pip install uv
uv python install 3.12
uv sync --locked --python 3.12

Después de sincronizar el entorno:

uv run --extra gui aovguard-ui
uv run aovguard --help

La CLI base sólo requiere NumPy y OpenEXR, sin Qt ni OpenCV. El extra opcional gui instala PySide6; usa uv sync --locked --extra dev para el entorno completo de desarrollo y pruebas.

python -m pip install ./dist/rc-wheel/aovguard-1.4.0rc1-py3-none-any.whl
python -m pip install "./dist/rc-wheel/aovguard-1.4.0rc1-py3-none-any.whl[gui]"
Importante: AOVGuard no crea EXR de demostración durante la instalación ni el análisis. La carpeta examples se conserva vacía salvo por su marcador de control de versiones.

Uso de la interfaz gráfica

  1. Selecciona la fuente. Usa File para un EXR o Folder para una secuencia.
  2. Carga un preset opcional. Puede ser TOML o JSON. Sin preset se aplican las reglas predeterminadas.
  3. Elige el modelo de luminancia. Selecciona Rec.709, Rec.601, ACEScg/AP1 o pesos personalizados según los primarios de los datos lineales. Elegir pesos no aplica una transformación de color.
  4. Configura el origen. Auto infiere el tipo; Sequence exige frames numerados; Comparison trata los EXR como muestras independientes.
  5. Revisa el descubrimiento. Ajusta patrón, búsqueda recursiva, profundidad, múltiples secuencias, límite y rango esperado.
  6. Presupuesto de memoria en desarrollo. Memory budget (MiB) usa 0 / Unlimited para desactivar, valor inicial de configuraciones nuevas o antiguas. Un valor guardado inválido activa 1024 MiB con una advertencia visible.
  7. Controles de ejecución en desarrollo. Mantén Isolate analysis process activado (valor inicial). Frame timeout (s) usa 0 / No timeout o un plazo positivo de servicio por frame. Desactivar aislamiento impide usar timeout y deja la cancelación nativa como cooperativa.
  8. Usa Inspect Structure. Comprueba resolución, partes, canales, AOVs y categorías antes de leer píxeles.
  9. Ejecuta Analyze. El progreso indica frames procesados y los errores de lectura se conservan como hallazgos.
  10. Revisa y exporta. Filtra hallazgos, navega a outliers y genera JSON o HTML.

Interpretación de la fuente

Auto

Resuelve archivo único, secuencia numerada o conjunto de comparación según los nombres encontrados.

Sequence

Activa validación de gaps, duplicados y padding. No admite mezclar frames numerados con EXR sueltos.

Comparison

Compara muestras deliberadamente independientes y evita declarar como gap una diferencia de nombres.

En modo aislado, Cancel detiene y recoge el proceso hijo activo. Cerrar espera la limpieza del hijo/hilo con el bucle de eventos activo. Se reutiliza un proceso secuencial; un timeout o caída falla el frame exacto y permite reemplazarlo para el siguiente. Una preferencia inválida restaura el aislamiento; un timeout guardado inválido selecciona 30 segundos con aviso visible.

Secuencias y rango esperado

El verificador agrupa nombres por el último bloque numérico anterior a .exr. Por ejemplo, shot.0001.exr y shot.0002.exr forman el patrón shot.####.exr.

Frame Limit y Expected Frame Range no son lo mismo

OpciónPropósitoEjemplo
Frame LimitEvita iniciar un análisis más grande de lo previsto.Rechazar si se descubren más de 1.000 archivos.
Expected Frame RangeDeclara qué números deben existir en una sola secuencia.Con 1–800 y sólo 1–301 presentes, reporta 302–800 como ausentes.

La ausencia dentro del rango esperado es un error. Los frames encontrados fuera de ese rango generan una advertencia. Esta opción no debe usarse en modo Comparison.

uv run aovguard check-sequence "C:\renders\shot" --expected-frame-range 1 800

check-sequence sólo revisa nombres; no decodifica píxeles. Devuelve código 1 si faltan frames o existen números fuera del rango declarado.

Admisión de memoria por frame, aún no publicada

uv run aovguard analyze ./renders --max-memory-mb 4096 --json ./reports/report.json --html ./reports/report.html

El presupuesto positivo y finito usa MiB (1.048.576 bytes) y admite fracciones. Omitir la opción lo desactiva; CLI 0 es inválido. Las cabeceras completas consideran todas las partes flat y canales físicos, incluidos unknown, ignored, alfa/AUX y Cryptomatte. La categoría o selección de AOVs no reduce la estimación. Un frame por encima del presupuesto falla antes de los píxeles con memory_budget, conserva cabecera/desglose y ruta exacta; los demás continúan. Un error de cabecera no activa una lectura sin protección.

El modelo flat-working-set-v1 cuenta 4 bytes nativos + 4 de promoción + 8 de stacks por canal/píxel, 32 bytes de temporales por píxel de la parte almacenada mayor y 64 MiB de reserva fija; después aplica 1,25 y redondea hacia arriba. Utiliza dataWindow y promoción conservadora sin afirmar tipos de píxel exactos desde la cabecera. No limita RSS global/duro: historiales, objetos GUI, decoder y cambios concurrentes siguen fuera de un límite garantizado.

Cómo interpretar los resultados

Findings

Errores, advertencias e información. Incluye regla, AOV, canal, archivo y evidencia.

Metrics

Métricas agregadas de AOVs de color y gráfica por frame con mediana y rango robusto.

Outliers

Muestras ordenadas por puntuación robusta. El botón de localización lleva al frame exacto.

Frames / Samples

Luminancia, valores no finitos y cambio respecto a la mediana y al frame anterior.

Technical

Mínimo, promedio, máximo, NaN, infinitos y negativos para cada canal técnico.

Sequences

Patrón, rango descubierto, presentes, ausentes, duplicados y padding.

Estados

  • PASS: no existen errores ni advertencias activas.
  • WARNING: hay condiciones que requieren revisión, pero pueden ser válidas para el plano.
  • FAIL: existe al menos un error, por ejemplo un EXR corrupto, NaN/Inf o un rango esperado incompleto.

La gráfica permite alternar entre luminancia, delta respecto al frame anterior y porcentaje relativo. Los triángulos indican outliers robustos y los cuadrados, errores de frame.

Tratamiento de Cryptomatte

Los valores de identificación de Cryptomatte se almacenan como números de punto flotante, pero no representan color ni brillo. AOVGuard consulta metadatos con la forma cryptomatte/<id>/name para reconocer la capa base y sus capas numeradas.

  • Los AOVs Cryptomatte se conservan en el inventario y en diagnósticos técnicos.
  • Todos sus canales ID y coverage continúan disponibles para comprobar NaN e infinitos.
  • No participan en luminancia, cambios temporales, outliers de brillo ni reglas genéricas de magnitud extrema.
  • Valores enormes o negativos de ID no se consideran por sí mismos un defecto.
Archivo sin metadatos: si un renderer elimina los atributos Cryptomatte, clasifica el AOV mediante [aov_categories]. AOVGuard evita asumir que todo nombre que empiece por crypto_ es Cryptomatte.

Categorías de AOV

CategoríaTratamiento
colorLuminancia, no-black ratio, series temporales y diagnóstico por canal.
scalar, vector, mask, depthTodos los componentes se diagnostican por canal; no se aplica luminancia de color.
cryptomatteIntegridad por canal sin interpretar IDs como intensidad.
unknownSe conserva y se señala; nunca se descarta silenciosamente.
ignoredDecisión explícita del usuario; permanece visible y conserva comprobaciones de integridad.

Reglas y presets

Un preset permite activar reglas, cambiar severidades, establecer parámetros y clasificar AOVs. Los nombres de [aov_categories] no distinguen mayúsculas y minúsculas.

preset = "entrega_iluminacion"

[aov_categories]
custom_depth = "depth"
crypto_asset = "cryptomatte"
vendor_payload = "ignored"

[rules.nan_inf]
enabled = true
severity = "error"
supported_aov_types = ["color", "scalar", "vector", "mask", "depth", "cryptomatte", "unknown", "ignored"]

[rules.empty_aov]
enabled = true
severity = "warning"
supported_aov_types = ["color"]

[rules.extreme_values]
enabled = false
severity = "warning"

[rules.extreme_values.parameters]
max_absolute = 1000000.0

Las reglas de integridad pueden aplicarse a canales técnicos. Las reglas artísticas como empty_aov y near_empty_aov se limitan a color. La interfaz permite guardar una clasificación desconocida en el preset únicamente después de una confirmación explícita.

Rangos técnicos por AOV

La regla de desarrollo technical_range está desactivada por defecto. Permite fijar límites inclusivos para cada AOV depth, mask, scalar o vector del proyecto. Comprueba todos sus componentes y muestra el frame y canal afectados en Findings, JSON y HTML.

[rules.technical_range]
enabled = true
severity = "warning"

[rules.technical_range.parameters.ranges.Z]
min = 0.0

[rules.technical_range.parameters.ranges.matte]
min = 0.0
max = 1.0
tolerance = 0.000001

Añade estas tablas a un preset con nan_inf activo y clasifica matte = "mask" en [aov_categories] si corresponde. Los nombres son ejemplos: usa los AOVs reales y las unidades del proyecto. El preset sustituye las reglas predeterminadas; conserva las demás comprobaciones que necesites.

Los rangos requieren al menos min o max finito. La tolerancia es absoluta, no porcentual, y vale cero si se omite. Los nombres distinguen mayúsculas y deben coincidir exactamente, sin comodines; para multipart usa la clave completa entre comillas, como "[part:left]::Z". Un destino no encontrado en ninguna inspección, una configuración inválida o una categoría no técnica generan rule_error. Para exigir presencia en cada frame usa también missing_aov.

En la interfaz carga el preset y activa Technical ranges. La regla reutiliza mínimos y máximos finitos: no vuelve a leer píxeles, no los modifica y no cuenta ni localiza los píxeles fuera de rango. Cryptomatte, color y canales desconocidos o ignorados quedan fuera de esta política. No se infieren unidades ni se valida la longitud de vectores.

Línea de comandos

Inspección estructural

uv run aovguard inspect-structure "C:\renders\shot.0001.exr"

Análisis con JSON y HTML

uv run aovguard analyze "C:\renders\shot" --source-mode sequence --expected-frame-range 1 800 --rules-config config\rules.example.toml --json reports\shot.json --html reports\shot.html

Descubrimiento recursivo

uv run aovguard analyze "C:\renders" --frame-pattern "shot.*.exr" --recursive --max-depth 2

Por seguridad, múltiples secuencias numeradas requieren --allow-multiple-sequences. Usa --max-frames 1000 como límite de tamaño y --fail-on-warning para publicación estricta.

Ejecución aislada y timeout, aún no publicados

uv run aovguard analyze ./renders --frame-timeout-seconds 60 --max-memory-mb 4096 --json ./reports/report.json
uv run aovguard analyze ./renders --in-process --json ./reports/in-process.json

El análisis canónico CLI/GUI usa por defecto un proceso hijo secuencial reutilizable. El timeout opcional, positivo y finito, empieza tras su señal de listo e incluye cabeceras, admisión de memoria, decode nativo, reducciones e IPC. El arranque tiene un plazo separado de 30 segundos; arranque/limpieza pueden sumar tiempo. Omitir timeout deja duración ilimitada por frame, no desactiva aislamiento. frame_timeout o worker_crash falla el frame exacto, recoge el hijo y permite reiniciar para el siguiente.

--in-process desactiva aislamiento, no puede interrumpir I/O nativo y rechaza un timeout simultáneo antes del decode. La API Python genérica conserva activación explícita con AnalysisOptions(isolate_frames=True, frame_timeout_seconds=60); un lector personalizado aislado necesita una especificación de proceso compatible. No se añaden paralelismo, caché, sandbox de seguridad ni límite RSS duro.

Los scripts API aislados deben llamar al análisis desde una función bajo if __name__ == "__main__":. En notebooks/REPL usa la API in-process inicial o una CLI externa, sin fallback silencioso. Los controles se aplican al análisis canónico, no a inspección de cabeceras independiente ni comandos legacy.

Descubrimiento, reglas finales y exportación también se ejecutan en el padre fuera del plazo por frame. Listar una carpeta/NFS lenta o usar Inspect Structure manual no tiene un límite duro de tiempo total mediante esta opción.

Códigos de salida

  • 0: PASS, o WARNING si no se solicitó modo estricto.
  • 1: FAIL, error de lectura/configuración o WARNING con --fail-on-warning.
  • 130: Ctrl+C durante el análisis canónico, tras limpiar el hijo.
  • 2: sintaxis inválida u opciones in-process/timeout incompatibles.
  • check-sequence también devuelve 1 ante un rango esperado incompleto.

Reportes y comparación baseline

JSON es el reporte canónico para máquinas y usa el esquema de análisis 1.2. Registra versión, opciones, reglas efectivas, fuente, frames descubiertos/procesados/fallidos, inventario de AOVs, métricas por frame y canal, nombre/vista/ventanas originales de cada parte, series separadas por secuencia y hallazgos sin emitir tokens NaN/Infinity no estándar.

HTML presenta el mismo resultado para revisión humana. Incluye estado, configuración, métricas, diagnóstico técnico, secuencias, hallazgos y recomendaciones.

La versión de desarrollo publica cada reporte mediante un archivo temporal y reemplazo atómico. Si la escritura falla antes del reemplazo, conserva el reporte anterior. Esta protección es automática en JSON, HTML, comparación y exportaciones antiguas JSON/CSV.

Los destinos no pueden ser EXR, enlaces simbólicos, archivos de solo lectura ni entradas conocidas. La CLI rechaza rutas de salida duplicadas, incluidos alias de archivos; la GUI también protege presets usados en análisis y baselines cargados en la ventana. Si la exportación falla por permisos o un archivo bloqueado, el análisis permanece disponible para volver a exportarlo.

La garantía es por archivo: si JSON se guarda y HTML falla, JSON queda guardado. No hay bloqueo entre escritores, garantía ante cortes eléctricos ni certificación de almacenamiento en red. Un cierre forzado puede dejar un temporal .tmp; los reportes completos existentes no se truncan durante la escritura.

uv run aovguard compare-reports reports\baseline.json reports\candidate.json --json reports\comparacion.json

La comparación muestra AOVs añadidos o eliminados, cambios métricos, hallazgos nuevos y problemas resueltos. En la GUI, analiza primero la versión candidata y después usa Compare Baseline.

Se rechazan configuraciones registradas que contradigan pesos de luminancia, umbrales, categorías, interpretación de la fuente o reglas activas. Las reglas desactivadas no afectan la compatibilidad; cambiar límites de un rango activo sí la afecta. Una métrica ausente o no finita se marca unavailable, no unchanged. Se pueden leer esquemas de análisis 1.0, 1.1 y 1.2, con una advertencia cuando no se puede verificar toda la compatibilidad histórica. Los hallazgos consideran archivos afectados relativos a la fuente y evidencia métrica; el reporte de comparación conserva su propio esquema 1.0.

Todos los canales físicos compatibles reciben controles de integridad, incluidos alfa y componentes auxiliares; los arrays UINT conservan IDs enteros exactos. Si RGB raíz y una capa beauty coinciden, el grupo raíz se muestra como beauty [root]. Los deltas temporales de secuencias numeradas requieren frames consecutivos y no atraviesan frames ausentes o fallidos.

Las partes multipart flat permanecen separadas: los nombres únicos generan identidades como [part:left]::beauty, con escape porcentual para delimitadores. Las partes sin nombre o con nombres repetidos utilizan el índice de parte. Se conservan nombre, vista y ventanas de cada parte. Cualquier parte deep o lectura incompleta invalida el frame completo; las reglas de resolución y estructura mantienen baselines separados por secuencia numerada.

uv run aovguard analyze ./renders --luminance-model acescg --json ./reports/acescg.json

ACEScg espera RGB lineal AP1 y utiliza pesos Y (0.2722287168, 0.6740817658, 0.0536895174). Los pesos --luminance-weights R G B sustituyen al modelo seleccionado.

Los campos de memoria de desarrollo son aditivos al esquema 1.2: metadata.options.max_memory_mb, modelo/unidades/advertencia y memory_estimates por archivo. HTML muestra presupuesto y decisión de admisión. El presupuesto no es una restricción semántica del baseline para métricas aceptadas, aunque cambiar los frames admitidos puede alterar agregados y hallazgos.

Los campos de ejecución también son aditivos: metadata.options.isolate_frames, metadata.options.frame_timeout_seconds y frame_execution por archivo (modo, estado, PID, segundos transcurridos, timeout, código de salida y etapa). HTML muestra esos diagnósticos. El tiempo puede incluir arranque, servicio del frame y limpieza; no es un benchmark exclusivo de decode. PID/tiempos volátiles y política de ejecución no afectan la compatibilidad baseline cuando la evidencia numérica coincide; los frames fallidos sí pueden cambiar hallazgos y agregados.

Solución de problemas

“EXR contains no image parts”
El archivo está vacío, incompleto o corrupto. AOVGuard lo marca como error de lectura y continúa con los demás frames; vuelve a renderizar o reemplaza ese EXR.
No se encuentran archivos
Comprueba la ruta y Frame Pattern. Activa búsqueda recursiva si los EXR están en subcarpetas y aumenta Max Depth si es necesario.
Se detectan varias secuencias
Restringe el patrón o selecciona una carpeta más concreta. Habilita múltiples secuencias sólo cuando combinarlas sea intencional.
Cryptomatte aparece como color
Revisa si el archivo conserva los atributos cryptomatte/.../name. Si no existen, asigna cryptomatte mediante el preset.
Valores técnicos extremadamente grandes
Pueden ser IDs codificados. La tabla usa notación científica; decide según la categoría y no por la magnitud aislada.
La interfaz parece congelada
Mantén aislamiento activado en la carpeta de desarrollo. Cancel detiene y recoge el hijo activo; cerrar espera limpieza de hijo/hilo sin bloquear el bucle de eventos. El modo in-process necesita esperar el retorno de la lectura nativa.
frame_timeout o worker_crash
Revisa archivo exacto, etapa y código de salida. Comprueba entradas incompletas, latencia de almacenamiento o un plazo demasiado corto; amplíalo deliberadamente cuando corresponda. El frame fallido queda registrado y los siguientes pueden reiniciar en otro hijo.
WorkerCleanupError fatal
La limpieza no pudo confirmar que hijo/receptor terminaran. Aborta el trabajo, impide reutilizar el executor y bloquea nuevos análisis en la GUI. Comprueba detalles de PID/error y cualquier proceso de análisis restante; después reinicia AOVGuard sin terminar trabajos Python ajenos. Las esperas acotadas no garantizan que el sistema operativo termine un proceso imposible de detener.

Limitaciones conocidas

  • Multipart flat está soportado. Deep sigue fuera de alcance; cualquier parte deep o decodificación parcial invalida el frame completo.
  • La identidad de nombres únicos es estable mientras el archivo sigue siendo multipart. Al pasar de dos partes a una, regresan las claves históricas sin prefijo. Los nombres ausentes/repetidos dependen del índice y su reordenación resulta ambigua.
  • La herramienta no comprende intención artística; los umbrales deben calibrarse por producción.
  • La inferencia de categorías es conservadora. Los nombres específicos del estudio pueden necesitar un preset.
  • El rango esperado admite exactamente una secuencia numerada y no reemplaza un sistema de gestión de granja.
  • Los reportes baseline comparan evidencia de AOVGuard; no realizan comparación visual de imágenes.
  • La API nativa carga los píxeles de todas las partes. Las referencias se liberan tras medir el frame, pero eso no demuestra streaming ni una reducción medida de RSS máximo. Los benchmarks pequeños no prueban capacidad 4K.
  • Las métricas cubren los píxeles almacenados en dataWindow; la resolución de entrega usa displayWindow. Un autocrop puede alterar la luminancia media sin cambiar el lienzo de entrega.
  • El espacio de color se selecciona explícitamente. ACEScg puede contener valores negativos válidos; sus umbrales necesitan contexto de producción.
  • El guard estima admisión, no un límite global/duro. La fuente puede cambiar entre cabecera y píxeles. Aislar permite detener el hijo, pero no constituye sandbox de seguridad ni límite de asignación; el I/O nativo in-process sigue sin poder interrumpirse. Caché, procesamiento paralelo, semántica automática por renderer y virtualización de tablas siguen pendientes.
  • El timeout cubre servicio tras la señal de listo, no arranque/limpieza ni tiempo total del trabajo. El arranque tiene un plazo separado de 30 segundos; cada frame tiene duración ilimitada por defecto.
  • La limpieza de hijo/receptor no confirmada es fatal y detiene el trabajo en lugar de sustituir silenciosamente el worker. Un proceso que el sistema operativo no pueda detener queda fuera de un plazo de terminación garantizado.

Repetir una verificación

uv run --locked python -m scripts.verify_real_sequence RENDER_FOLDER --frame-pattern "Venator_v20_xpu_passes.*.exr" --expected-frame-range 1065 1208 --luminance-model rec709 --expect config/verification/venator-master.json --output-directory dist/verification-venator-new --gui --check-cancellation

Sustituye RENDER_FOLDER por tu carpeta externa y usa un destino nuevo. Los perfiles de config/verification describen resultados esperados, no presets que oculten advertencias. El control predeterminado compara nombres, tamaños y fechas; --hash-source añade SHA-256 antes y después. Los reportes completos y las rutas privadas permanecen fuera del repositorio público. El verificador y sus opciones se distribuyen en el checkout o ZIP de código.

Preparar un paquete de desarrollo

El generador conserva los archivos necesarios para ejecutar las pruebas, excluye EXR, reportes locales, cachés y patrones comunes de archivos privados, y añade un manifiesto con tamaño y SHA-256 de cada archivo. Revisa la selección y el contenido antes de compartir: estos filtros no son un detector de secretos.

python scripts/create_release.py --list
python scripts/create_release.py --output dist/AOVGuard-development-source.zip
python scripts/create_release.py --verify dist/AOVGuard-development-source.zip

Solo requiere Python 3.11/3.12 estándar. Verifica el ZIP antes de publicarlo en el destino y nunca sobrescribe un archivo existente. Requiere un sistema de archivos con enlaces duros, como NTFS local; si no están disponibles, falla sin recurrir a una escritura destructiva. El manifiesto comprueba integridad, no autenticidad, y el verificador no extrae ni ejecuta archivos. La reproducción byte a byte requiere los mismos archivos y el mismo entorno Python/zlib, sin ediciones durante el empaquetado. Es un snapshot de desarrollo, no una nueva versión estable publicada; los ZIP antiguos sin manifiesto quedan fuera de esta verificación.

Este comando de sólo lectura mide RSS máximo nativo en un proceso hijo aislado con EXR existentes. No genera imágenes ni reportes; rechaza fuentes demasiado grandes en lugar de muestrearlas. El CI exige 95 % de cobertura combinada e incluye lint, tipos, wheel e instalación CLI aislada. Los tests usan fixtures temporales y examples mantiene únicamente .gitkeep.

El hito previo de admisión de memoria tuvo 523 superadas, 1 omitida y 95,81 % de cobertura combinada en cada ejecución Windows/Python 3.11.14 y 3.12.12; mypy configurado cubrió 43 módulos.
